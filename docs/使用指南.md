# 使用指南

面向操作的说明。构建、烧录、命令参数见 `README.md`。

## 一、上手三步

1. 板子上电，手机开蓝牙。
2. App 顶部点「搜索板子」。列表出现 `rftool-c5` 就点它；扫不到点「系统蓝牙」，用系统选择框连。
3. 连上后顶部显示 `已连接`，画布左下角开始出现板子回传的日志。

顶部三格按钮的分工：「搜索板子」按服务 UUID 扫，速度慢但准确；「系统蓝牙」直接拉系统选择框，广播内容被降级时用它。

## 二、界面结构

```
┌──────────────────────────────────┐
│   RFKitCN112          已连接     │  ← 左上角打开导航
│ CH 6   AP 12  SNIFF 0  ...        │  ← 全局读数
├──────────────────────────────────┤
│ 搜索板子 │ 系统蓝牙 │  断开        │  ← 连接
├──────────────────────────────────┤
│ 目标  某热点  BSSID·CH·dBm  [扫描][更换] │  ← 目标条
├──────────────────────────────────┤
│                                   │
│   当前功能（一页只放一个任务）        │
│                                   │
│   ───── 该页要点 ─────             │

│ 设备输出  自动 调试 复制 清空 导出   │  ← 日志

```

导航在左侧抽屉，点左上角 ☰ 展开，7 个分类按使用顺序排列：

| 分类 | 页面 |
|---|---|
| 概览 | 仪表盘 |
| 目标 | 扫描热点、已连客户端、BLE 近邻 |
| 嗅探 | 嗅探与握手、原始帧落盘 |
| 注入 | Deauth 断开、Beacon 洪泛、Probe 洪泛 |
| 诱捕 | 钓鱼门户、Evil Twin、KARMA、WPA3 降级 |
| 工具 | 一键编排、原始帧构造、BLE 广播伪造、FTM 测距、信号定位、802.15.4 嗅探、BLE 发射功率 |
| 系统 | 连接信息、数据库快照、导出、板载 HTTP、固件升级、诊断、关于、CLI 控制台、指令速查 |

抽屉顶部有过滤框，输入「握手」「定位」「ota」能直接跳。

每页只放一个任务，个别有前置关系的合成一页（嗅探与握手、门户与自定义页）。内容不超过一屏，不需要滚动找按钮。

## 三、目标从哪来

所有需要 AP 或 MAC 的功能共用同一个「目标」。取目标只有两条路径：

1. 点目标条右边的「扫描」，直接开始 6 秒扫描，扫完在列表里点一条热点。
2. 导航 →「扫描热点」，点「快速扫描 6s」或「深度扫描 15s」，再点列表里的热点。

选中后目标条显示 SSID、BSSID、信道、信号强度。Deauth、降级、钓鱼、Evil Twin、一键编排、信号定位、FTM 这几个页面的目标字段会自动填好，不用重复挑。

需要手动改时，点输入框弹出候选列表，按信号强度排序，也可以直接粘贴。

## 四、抓 4 次握手

前置：无。

1. 选目标（可以是整台 AP，不必逐条看客户端）
2. 导航 →「嗅探」→「开始嗅探」，信道选 `AUTO 轮询`
3. 看「EAPOL 握手」里的 `可破解` 计数
4. 计数大于 0 时点「导出 .hc22000」，得到 hashcat 能直接吃的文件

握手只在嗅探或 Deauth 期间产生。计数一直为 0 通常有两个原因：附近没有客户端在重连（这时去 Deauth 踢一下），或者目标是纯 WPA3（没有四次握手）。

Deauth 完成后 App 会进入 15 秒握手等待窗口，收到匹配目标的 EAPOL 才算成功，否则显示「已发出，等待确认」。窗口内没有握手就提示换路线（降级或 Evil Twin），因为目标多半开了强制 PMF。

目标支持 PMKID 时可以不踢客户端：`pmkid active <bssid|ssid> --yes` 以 station 身份关联一次，AP 回的 M1 带 PMKID 就直接入库。结果看 `META,PMKID,ACTIVE,ok,1,m1,1,pmkid,1` 这一行：`m1=1, pmkid=0` 表示握手抓到了，但这台 AP 不下发 PMKID，改用 `pmkid watch` 等真实客户端漫游。

## 五、踢客户端下线

前置：目标必须在扫描列表里。

1. 选目标
2. 导航 →「注入」→「Deauth 断开」
3. STA 留空是广播，会踢掉该 AP 下所有客户端；填具体 MAC 只踢一个
4. 次数默认 10，间隔 100ms，够用。连不上就翻倍再试

PMF 必需的 AP 会被固件直接拦下，界面提示改走「WPA3 降级」或「Evil Twin」。这是固件行为，App 不参与判断。

降级前先 `downgrade list`：只有「同时宣告 PSK 与 SAE、且 MFP 非必需」的过渡模式 AP 才降得动，强制 PMF 的纯 SAE 目标不在列表里。

注入前先看信道忙不忙：`airtime --band 2g` 逐信道驻留 300ms，输出占用率、帧数、最强 RSSI。只看 AP 数量不够，一台 AP 刷视频也能把信道占到 60%。窗口低于 200ms 会报 `dwell_short`，因为 beacon 间隔 102ms，太短会把「有 AP 但没扫到」当成空信道。

目标开了强制 PMF 时 deauth 走不通，换 CSA：`raw csa <bssid> <new_ch> [次数] --yes`。固件先在空中抓一份目标的真实 beacon（RSN 与 HT/VHT/HE 能力原样保留），末尾追加 CSA IE，在目标信道连发，倒计时从次数递减到 1。beacon 不在 PMF 的保护范围里，客户端会照做。先加 `--dry` 看组出来的帧，确认无误再去掉。

`--dry` 输出 `META,CSA,DRY` 与整帧十六进制；实发输出 `META,CSA,TX`，带 `sent/fail/cloned`。`cloned=0` 表示没抓到目标 beacon，用的是合成帧，通常只在开放网络或目标信号太弱时出现。

## 六、搭钓鱼门户

前置：选目标。门户 SSID 自动跟随目标，用真热点同名，手机更容易自动连。

1. 导航 →「诱捕」→「钓鱼门户」
2. 确认热点 SSID，密码留空表示开放网络
3. 点「启动门户」
4. 让测试手机连上这个热点，打开任意网页会跳到认证页
5. 提交的账号密码出现在页面下方的「捕获的凭据」

换成自己的认证页：同一页往下，「自定义认证页」选 HTML 文件 →「上传到设备」，上限 1MB。「恢复内置」换回默认模板。

门户独占射频，启动时会停掉嗅探和注入。

## 七、判断目标有没有开 PMF

1. 选目标
2. 导航 →「工具」→「一键编排」，点「PMF 判定」

输出说明该 AP 是强制 PMF、可选，还是没开。强制 PMF 的 AP 对广播 Deauth 免疫，别浪费次数。

## 八、测距离与找方向

**FTM 测距**（需要 AP 支持 802.11mc）

导航 →「工具」→「FTM 测距」，选目标，点「开始测距」。结果给出米数与置信区间。不支持 802.11mc 的 AP 会直接失败。

**信号定位**（任何目标都能用）

导航 →「工具」→「信号定位」，点「开始采样 30s」。采样期间拿着设备走动，结束后看 `avg / min / max / trend`。趋势上行表示靠近。单台设备测不出方向，只能靠走动比较强弱。

「导出 CSV」拿到 `t_ms,rssi,channel` 三列，可以自己画图。

## 九、抓原始帧给 Wireshark

1. 导航 →「嗅探」→「原始帧落盘」→「开始落盘」
2. 抓够之后「停止」，再点「拉取关键帧」（只要 EAPOL、PMKID、Deauth）或「完整 pcap」
3. 文件用 Wireshark 打开

落盘写在板载 Flash，8MB 分 512KB 段轮转。每次开始落盘会切到下一段，所以上一次的数据不会被立刻覆盖，但也不保证还在。要保留就先拉走。

文件是 radiotap 格式（linktype 127），每条记录带信道、频率、RSSI、噪声和速率，Wireshark 里可以直接按 `wlan_radio.channel` 过滤，也能看信号强度。没有射频元数据的裸 802.11 格式（linktype 105）已经不用了。

串口调试可以 `cap hex <off> <len>` 直接看十六进制，不必连手机。

完整 pcap 需要板载 HTTP 服务在跑（系统 →「板载 HTTP」→「启动」），数据量大时走 HTTP 比 BLE 快。

## 十、升级固件

**方式一：板载 HTTP 上传**

1. 系统 →「板载 HTTP」→「启动」，记下 SSID 与密码
2. 手机连这个热点，浏览器打开 `http://192.168.71.1`
3. 填入 token（CLI 里 `config get api_token`），选 `rftool.bin` 上传

**方式二：设备自己下载**（需要板子能出网）

CLI 里 `ota url http://192.168.1.10/rftool.bin`，只支持 http。

升级后重启生效。新镜像第一次启动有 45 秒观察期，期间不崩就自动确认；崩了引导器回滚到旧分区。状态用「固件升级」页的「查询状态」看，`running` 和 `boot` 两个槽位不一致说明切过去了但还没确认。

## 十一、看链路质量

导航 →「系统」→「连接信息」，页面给出连接建立后协商出来的三个数：

| 读数 | 含义 | 正常值 |
|---|---|---|
| MTU | ATT 最大传输单元，App 按它切分下发 | `256` |
| PHY | BLE 物理层，`1`=1M（默认）`2`=2M | 连上后 `2` |
| RSSI | 连接后的信号强度 | 高于 -85dBm |

PHY 走到 `2` 表示 2M 协商成功，同样长度的指令少占一半空口时间，传输时间直接减半；一直是 `1` 也能用，只是吞吐低，App 会自动按 1M 的量切分，不会丢字节。

想直接读原始值，CLI 或 App 控制台执行 `status`，返回行末尾带 `,mtu,xx,phy,x`。

## 十二、看 Wi-Fi 6 结构

`wifi6` 列出所有 11ax AP 的 BSS Color、TWT Required 与 6GHz 邻居（从 RNR 反推）。

BSS Color 是空间复用标记：同色 + 同信道 + 两边信号都强，才会互相把对方的帧当成自己人。同一个物理 AP 常发多个 BSSID，这些同色是正常的，输出里标 `same_dev,1`，不计入冲突数。

TWT Required 是 AP 的策略位，实际协商在 TWT Action 帧里，beacon 里通常没有 TWT 元素，所以 `twt_ie` 常年是 0。

## 十三、命令行与指令速查

「系统」→「CLI 控制台」输入命令，回车下发，↑/↓ 翻历史。固件的输出原样回显；命令失败时设备会回一行带原因的拒绝，App 把它翻成人话显示，不会停在「设备无响应」。

「系统」→「指令速查」列出全部命令与用法，点一行填进控制台，参数可以再改。命令名标红的是破坏性操作，固件要求带 `--yes`，不带只回一条拒绝、不执行。

常用命令：

| 命令 | 用途 |
|---|---|
| `status` | 状态与计数器，App 每 3 秒自动拉一次 |
| `sniff 6` / `sniff auto --dwell 300` | 定信道 / 全信道嗅探；auto 默认按每信道发现数排序，`--policy wrl` 回到旧的帧率加权 |
| `dump aps` | 读设备端 AP 表，`clients` / `eapols` / `all` 同理 |
| `hs 22000` | 导出 hashcat 22000 |
| `deauth -b <bssid> -n 10 --yes` | 踢客户端，不带 `-s` 为广播 |
| `scenario pmf <bssid>` | 判 PMF 并给下一步路线 |

## 十四、CSI 动作感知

`csi start [ch]` 在固定信道上开始采集 CSI，`csi stop` 停止，`csi stats` 看采样率与子载波数，`csi raw <n>` 把原始 I/Q 打成十六进制。

判定方式：每来一帧把 52 个子载波的幅度归一化，跟同一个源 AP 的上一帧比，差值超过该源基线的两倍且大于 0.15 就报 `motion,1`。两步都不能省：不按源 MAC 分开算，换 AP 的那一帧就是个大跳变；不归一化，AGC 增益逐帧跳，静态基线就有 40 上下。

现场实测：3 个源合计 39~89 帧/秒，单源 13~25 帧/秒；归一化后静态基线 0.07，12 秒 53 个采样点零误报。

`csi selftest` 灌一段合成序列验判定链路，输出 `result,pass,peak,0.185`。真实人体的检出率它验不了，要人在设备前面走：静止 60 秒记基线，走动 30 秒，重复 20 次，看检出率和虚警率。

采集期间不能同时嗅探或注入。采样率由环境里的 beacon 决定，想更高得另找一台设备发包。

## 十五、802.15.4（Zigbee / Thread）

### 先看有没有流量

`zbsniff <ch 11-26>` 在指定信道收帧，`zbsniff status` 看计数，`zbsniff dump` 把帧表打成十六进制。换信道直接再敲一次 `zbsniff <ch>`，不用先 stop。

16 个信道全扫过一遍之前先有个预期：802.15.4 信道 11-26 与 Wi-Fi 信道 1-13 占同一段 2.4GHz，但两者不互通，Wi-Fi 嗅探看不到 Zigbee，反过来也一样。家里没有 Zigbee 灯具、Thread 边界路由器的话，16 个信道大概率全是 0。

### 发帧

| 命令 | 作用 |
|---|---|
| `zbtx beacon <ch> [pan] [n]` | 伪造一个 Zigbee 协调器 beacon |
| `zbtx beaconreq <ch> [pan] [ms]` | 发 Beacon Request，然后留在信道上听回应，列出发现的 PAN |
| `zbtx data <ch> <dst_pan> <dst> <src> <hex>` | 单播数据帧，payload 自己给 |
| `zbtx raw <hex> [n]` | 原样发送，帧首字节是 MHR+payload 长度 |
| `zbtx replay <i> [n]` | 重放 `zbsniff` 表里第 i 条 |
| `zbtx flood <ch> [pan] [n]` | 每 100ms 一个 beacon，默认 100 个 |
| `zbtx stats` / `zbtx stop` | 计数 / 停止 |

所有实发都要 `--yes`，加 `--dry` 只组帧并回十六进制。`beaconreq` 会自动打开嗅探收集回应，收完把自己开的那份嗅探关掉；你自己开着的嗅探它不动。

### CCA 会被 Wi-Fi 挡住

802.15.4 的 CCA 是能量检测，而 802.15.4 ch11-26 与 Wi-Fi ch1-13 频率重叠。现场有 23 台 AP 的时候，实测 10 帧里只有 1 帧抢到窗口，其余报 `cca_busy`。命令默认退避重试 4 次（每次间隔 12ms），还不够就加 `--noca` 跳过空闲评估直接发。

### 与 Wi-Fi / BLE 的关系

802.15.4 与 Wi-Fi、BLE 分时共用同一套射频前端。启动 `zbsniff` 或 `zbtx` 前 CLI 会先停掉所有 Wi-Fi 作业；BLE 的 NUS 连接会断，因为控制器要把射频交给 802.15.4。两者不能同时要，这是硬件决定的，不是软件没做。

帧结构按 Zigbee NWK 规范构造（beacon payload = 协议ID + 版本/Profile + 容量 + 扩展PAN + TxOffset + UpdateId）。现场没有 Zigbee 设备，所以「客户端是否接受这个 beacon」没有实测，固件侧只能证明帧构造正确、发射完成。

## 十六、BLE GATT 枚举

「BLE 近邻」里先「开始扫描」，等设备出现后**点选**一台（再点一次取消选中），下方「GATT 枚举」点「枚举选中设备」。命令行等价于 `gatt <mac> --timeout 25000`。

输出按服务分段，每行一个属性：服务的句柄范围、特征的句柄与权限位（R 读 / W 写 / w 无响应写 / N 通知 / I 指示）、描述符，以及每个可读特征读到的值。值大于 0 字节时会附一段可打印文本，不可打印的字节显示成 `.`。

`gatt status` 看当前进度，`gatt stop` 中止。

### 三个要知道的事

**权限位不可读的特征会被跳过**，不会逐个去试。对不可读的特征发 read，设备回 ATT 错误之后 NimBLE 不一定还会调回调，状态机会卡死到总超时（实测小米体重秤 16 个特征里 13 个不可读，全试一遍要 40 秒以上）。

**描述符发现有可能被跳过**。部分设备对某些句柄范围不回 Find Information Response，NimBLE 的回调就再也不出现。这里加了步骤看门狗：一个步骤 1.5 秒没动静就按"已完成"推下一步，连续 6 次才判失败。所以 `result,FAIL` 时服务与特征通常还是全的，缺的是描述符和个别值。

**设备在句柄末尾回什么错误码并不统一**。规范是 `ATTR_NOT_FOUND`(0x0a)，实测小米体重秤回 `UNLIKELY`(0x0e)，但服务已经全拿到了。这两种码都当正常结束处理，其他的才判失败。

### 与 App 控制链的关系

枚举期间板子作为 central 连第三方，同时仍作为 peripheral 被手机连着（`CONFIG_NIMBLE_MAX_CONNECTIONS=2`）。两条连接互不影响，CLI 输出照常从 NUS 回来。改成 1 的话枚举会把 App 挤掉，堆实测没有额外代价，所以保持 2。

## 十七、BLE 弹窗模板

「BLE 广播伪造」里切到「弹窗」tab，选 Fast Pair / SwiftPair / Continuity 之一，填时长，点「开始伪造」。命令行等价于：

```
bleadv popup fastpair [modelid] [sec]
bleadv popup swiftpair [sec]
bleadv popup continuity [sec]
```

三类都是非连接广播，复用 iBeacon 那套挂起/恢复机制：广播期间 NUS 连接广播挂起，停止或超时后自动恢复。

**能不能真弹窗，取决于目标设备的系统，不是帧发出去就弹：**

- **Fast Pair**（安卓）：Service Data 0xFE2C，需要 Google 注册过的真实 Model ID 才会弹。缺省 0 是占位，Google 服务端查不到，手机不弹。填一个真实存在的 Model ID 才能触发，但 Google 有反滥用机制，同一设备 ID 短时间内反复广播会被拉黑。
- **SwiftPair**（Windows）：Manufacturer Data 0x0006，Windows 扫到会弹「附近有设备，点击连接」。这是三类里最直接的一种。
- **Continuity**（iPhone）：Manufacturer Data 0x004C type 0x07。真实弹窗需要加密的 offline-finding 数据与旋转 key，iOS 校验不过会静默丢弃，所以这个模板只是结构正确，弹窗概率最低。

帧结构按各家公开规范构造，广播发出与否固件侧能验证（NimBLE 返回成功），弹窗效果需要拿目标设备实测。

## 十八、常见问题

**搜不到板子**
先确认板子没在跑门户或嗅探导致射频被占。再试「系统蓝牙」。都不行就用串口 `version` 确认固件在跑。

**连上后所有按钮是灰的**
`未连接` 状态下控件全部禁用，这是有意的。确认顶部状态是 `已连接`。

**扫描扫不到 AP**
快速扫描 6 秒只覆盖主流信道。远处目标用「深度扫描 15s」。仍然为空就靠近一点，或者确认板子天线接好。

**握手一直 0**
见第四节。先确认有客户端在线（「已连客户端」页），没有客户端就不会有握手。

**操作被拒绝，提示 PMF**
目标开了 802.11w，广播 Deauth 无效。改走降级或 Evil Twin，或者确认这是预期行为后加 `--force`（CLI 里）。

**导出失败**
大数据量导出要先停嗅探，否则内存不够。pcap 类导出需要板载 HTTP 在线。

**日志里出现 `INJECT,SUPERSEDED`**
注入类任务（Beacon / Probe / Deauth）同时只能跑一个。已经有一个在跑时再发一个新的，固件会先收掉旧的再起新的，并打印这行。这是正常接管，不是报错，收尾的旧任务会带 `stopped,1`，新任务照常发完。

**连着连着按钮变灰**
App 12 秒收不到板子回包，会连发 3 次试探，都失败就判定断连并回到未连接状态。原因通常是人走远了，或者板子进了射频独占任务（门户、嗅探）。回到信号范围内点「搜索板子」重连即可。

**Beacon 洪泛的信道怎么指定**
页面和 CLI 都带 `-c/--channel`，不填就跟着当前信道。要把假热点广播到别的信道上才被目标看到时，填那台的信道。

**板载灯在慢慢明暗变化**
常态是呼吸灯，2.2 秒一个周期。告警和错误改用闪烁，与渐变一眼可分；抓到 EAPOL 之类的事件会短暂抢占成纯色再回落。
