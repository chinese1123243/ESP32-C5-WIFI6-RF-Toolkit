# 算法规划与代码审视

对应固件 2.4.9 / App 2.4.9, 2026-11-01。这份文档是给作者审的, 不是发布物。

## 一、代码审视

### 已修 (这轮)

**握手 M2+M3 配对从来没成立过** (`main/hs.c`)

`try_pair()` 要求 M3 与 M2 的 replay counter 相等。802.11 四次握手里 M3 的 counter
是 M2 的 +1, 所以「只抓到 M2+M3」这种最常见的情形一条 22000 都出不来, 而自检里
压根没有这个用例, 于是一直是绿的。现在接受 +1, 自检补了第 4 例
(`M2 + M3(counter+1)` 期望 `pair=m2m3`)。

这类问题跟 `hs.c` 当初把 KeyInfo 的 MIC 位写成 key type 是同一个坑: 自检帧必须
逐字节照线上抄。后面新增用例一律走这条规矩。

**Beacon 的 capability 字段是错的** (`main/radio_common.c`)

写的是 `0x2101`, 置上了 Spectrum Mgmt(0x0100) 与保留位(0x2000), 而注释写的是
ESS|ShortPreamble。改成 ESS|ShortSlot = `0x0401`, 与常见 AP 一致。

**注入换信道失败没有任何反馈** (`main/wifi_attack.c`)

`esp_wifi_set_channel()` 返回值被丢掉。失败时帧全落在旧信道上, 现象是「发了很多
一台没见」。现在失败出 `META,WIFI,INJECT,ERR,msg,set_channel_failed`。

**`flood -t auth -i 10` 丢帧 13/30** (`main/wifi_attack.c`)

驱动发送队列满返回 `ESP_ERR_NO_MEM`, 原实现直接丢弃。现在退避 20ms 重发同一帧
(最多 3 次), 把「间隔太密」和「射频异常」区分开。这是扫全里唯一一条长期的红。

**反向 deauth/disassoc 帧返回值未检查** (`main/wifi_attack.c`)

AP→STA 方向那一帧是直调 `esp_wifi_80211_tx()` 的, 失败既不计数也不上报。现在计入
`err`, 与正向帧一起出现在 DONE 行。

**OUI 表只有 40 条且有 5 条占位 Unknown** (`main/wifi_db.c`)

原来是手写表 + 线性查找, `0x28,0x15,0xA4` 这类条目直接写 "Unknown"。改为
`tools/gen_oui.py` 从 IEEE 注册表生成: App 侧 12166 条 (60 家精选, 不限条数),
固件侧 1963 条 (受 `vendor[16]` 与 flash 约束), 二分查找。

### 待办

| 级别 | 问题 | 位置 | 处理建议 |
|---|---|---|---|
| P1 | 注入的 `sent` 是「驱动收下」, 不是「上了空口」。用户看到 sent=30 但一台没断, 无法区分没发出去和发了没人理 | `wifi_attack.c` DONE 行 | 拆成 `sent`/`err`/`accepted` 三个字段并在 App 说明语义; 真要判空口只有抓自己的帧 |

## 二、算法规划

### 1 信道调度 (最有收益的一块)

现状：`psd` / `wrl` / `adt` 三策略。`adt` 是事件驱动 + 就地续期, 12 轮 A/B 的结论
只站住一条: 前 2 秒比 psd 多约 4 台 (区间 [+1.8, +6.2]), 3/5/8 秒持平。

瓶颈有两个, 都不在驻留公式上：

1. `p = 1 - exp(-e/102.4)` 把「驻留时间」当「曝光」。实际曝光还受 CCA 占用、重传、
   客户端省电模式影响, 同一段驻留里 beacon 可能只来了一半。
2. 尾延迟来自「被放弃信道上的最后一台 AP」。它要等下一轮回探, 而回探顺序是
   `rem/(dwell+20)` 的贪心, `rem` 里没有「还剩几台没找到」的量。

方案：

- 曝光折算 `e_eff = e * (1 - busy_ratio)`, `busy_ratio` 从驱动拿 CCA 占用。这一项
  不改策略, 只让 p 更接近真实。
- 剩余量估计：用 Good-Turing/Chao1 从「出现 1 次的 AP 数 f1」估 `n_hat`：
  `n_hat = f1^2 / (2*f2)`, f2 是出现两次的 AP 数。回探判据从「p 不够」改成
  「`n_hat` 还有余量且本信道贡献过 f1」。
- 首探长度不动。给满 base 会把一趟拖到 25 秒, 实机输 psd 3.2 台, 这个已经被
  真机否过一次。

验收：`chan_ab.py` 两组交替跑, 20 秒视界看找齐率与 p90, bootstrap 区间不跨 0 才算数;
仿真先过 `chan_sim.py` + `chan_oracle.py` 筛设计。90% 那条线不可达 (clairvoyant 上界
说明必须每条信道都去一趟), 只用来读「探索花了多少冤枉时间」。

### 2 信号定位

现状：截尾均值 (两端各去 20%) + MAD, 输出 med/mad/us, 趋势用前后 25% 中位数差。

瓶颈：只有点估计, 没有不确定度。mad 大的样本照样等权进趋势, 多径时趋势会反号。

方案：把 mad 当权重做加权最小二乘 (log-distance 路径损耗模型), 或在采样流上做
指数遗忘的贝叶斯更新, 先验取上一时刻位置。两者都不需要连续采样, 静止时不会漂。

验收：已知距离 1/3/5/10 米各采 60 秒, RMSE 目标 < 1.5dB; mad > 6dB 的窗口必须降权,
表现为趋势不再跟着离群点翻向。

### 3 CSI 动作检测

现状：非对称基线 (下行 0.02 / 上行 0.002) + mad 归一化 + CUSUM, 持续动作 100% 检出,
旧判据只有 1%。

瓶颈：输入是单个标量, 没有子载波维度, 环境变化 (开关门、有人坐下不走) 与真动作
在同一个尺度上, 只能靠基线跟随速度区分。

方案：取子载波方差 top-K 做联合判据, 用 2 秒窗的谱熵区分「人在动」与「环境漂移」。
代价是每次要算 K 路方差, 内部 RAM 只有 ~70KB, K 取 4 且在 PSRAM 上做。

验收：静止/走动/开关门三场景各 60 秒, 误报率 < 5%, 漏报率 < 10%; 只能真机, 仿真
做不出来。前提是 CSI 有数据, 未关联 AP 时收不到帧这条限制还在。

### 4 握手捕获

现状：8 槽, 键是 (AP, STA), 到达即配对并固化副本。

瓶颈：槽满就丢新目标, 早期弱信号目标会把槽占满。

方案：槽满时按「是否已完整」优先, 同档按 RSSI 淘汰。改动很小, 但能把弱目标挤出去。

验收：`test_inject.py` 20 项 + 真机抓一次完整 4-way。

### 5 诱捕与门户

现状：门户页内嵌 flash; KARMA 只收集 probe 的 SSID, 不做应答。

瓶颈：没有应答节流; App 侧只有列表, 看不出「谁在探什么」。

方案：真要回应答就加令牌桶 (每客户端 1pps), 现在没做, 不做也行。App 侧把
`karmaList` 做成时间线更划算, 零风险。

验收：单客户端 1 分钟内应答次数上限可复现。

## 三、测试矩阵

分三类用例, 每条都带「预期」：留空 = 应正常执行, `reject` = 固件必须挡回来。

扫全 (`scripts/test_sweep.py`) 共 127 条, 按族分布:

| 族 | 用例数 | 覆盖内容 |
|---|---|---|
| 扫描/嗅探 | 14 | scan / sniff 各信道与 auto / dump / status |
| 注入 | 24 | deauth、disassoc、auth、beacon、probe 五族的正常与非法参数 |
| 诱捕 | 11 | phish、karma、eviltwin、downgrade 的启停与前置条件 |
| 测量 | 8 | ftm、locate、csi 的采样与查询 |
| 无线 | 32 | raw 帧、bleadv 各类型、zbsniff/zbtx、ble 扫描与功率 |
| 数据 | 14 | cap 落盘、export csv/json、http 服务、config |
| 维护 | 12 | ota、health、selftest、version、reset |
| 其余 | 12 | help、log、job、stop、scenario |

每族都覆盖三类：正常参数、非法参数（应被 `reject`）、前置条件未满足（如没 scan
就 deauth）。判断依据全部来自固件回的 META 行, 不看"看起来正常"。

上面这支只验"没打死"。另加 `scripts/test_func.py` 验"真干成事"：嗅探有没有帧、
注入的 sent 对不对、门户起没起来、握手自检四条是否符合预期、落盘有没有抓到、
射频仲裁与事件总线有没有输出。

### 结果

| 项 | 结果 |
|---|---|
| 扫全 127 条 | 0 重启、0 致命、0 失败、41 条入参拒绝（都是预期） |
| 注入验收 20 项 | 20/20 |
| 功能结果 16 项 | 16/16 |
| 堆 before/after（扫全） | 33567 → 32627，三次独立跑都回到同一量级，是稳态不是泄漏 |

功能结果 16 项具体是：版本可读、health 字段齐全、嗅探有帧、轮询发现 AP、
beacon 30/30、probe 30/30、auth -i 10 30/30 不丢、未知目标被挡回、门户起来且带页面、
门户状态回报、握手自检 1/1/0/1、落盘抓到帧、CSI 自检 pass、CSV 有数据行、
射频仲裁有输出、事件总线有输出。

还没做的：`stress.py` 全量内存归因（9 族 × 3 轮，约 20 分钟），以及真实 4-way
握手的端到端验证（需要现场有一台在连的客户端）。

## 四、不建议做的

- 追 90% 找齐率。clairvoyant 上界说明现实策略首轮必须每条信道去一趟, 这条线在
  信道调度上不可达。
- 把 34k 条 OUI 全塞固件。flash 放得下, `vendor[16]` 放不下, 而且长厂名在 CLI 里
  更难读。
- 多射频并发。硬件就一个射频, 嗅探/注入/门户互斥是物理约束, 不是实现偷懒。
