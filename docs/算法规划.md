# 算法规划与代码审视

对应固件 2.4.9 / App 2.4.9, 2026-11-01。这份文档是给作者审的, 不是发布物。

## 一、代码审视

### 已修 (这轮)

**握手 M2+M3 配对从来没成立过** (`main/hs.c`)

`try_pair()` 要求 M3 与 M2 的 replay counter 相等。802.11 四次握手里 M3 的 counter
是 M2 的 +1, 所以「只抓到 M2+M3」这种最常见的情形一条 22000 都出不来, 而自检里
压根没有这个用例, 于是一直是绿的。现在接受 +1, 自检补了第 4 例
(`M2 + M3(counter+1)` 期望 `pair=m2m3`)。

这类问题跟 `hs.c` 当初把 KeyInfo 的 MIC 位写成 key type 是同一个坑: 自检帧必须
逐字节照线上抄。后面新增用例一律走这条规矩。

**Beacon 的 capability 字段是错的** (`main/radio_common.c`)

写的是 `0x2101`, 置上了 Spectrum Mgmt(0x0100) 与保留位(0x2000), 而注释写的是
ESS|ShortPreamble。改成 ESS|ShortSlot = `0x0401`, 与常见 AP 一致。

**注入换信道失败没有任何反馈** (`main/wifi_attack.c`)

`esp_wifi_set_channel()` 返回值被丢掉。失败时帧全落在旧信道上, 现象是「发了很多
一台没见」。现在失败出 `META,WIFI,INJECT,ERR,msg,set_channel_failed`。

**`flood -t auth -i 10` 丢帧 13/30** (`main/wifi_attack.c`)

驱动发送队列满返回 `ESP_ERR_NO_MEM`, 原实现直接丢弃。现在退避 20ms 重发同一帧
(最多 3 次), 把「间隔太密」和「射频异常」区分开。这是扫全里唯一一条长期的红。

**反向 deauth/disassoc 帧返回值未检查** (`main/wifi_attack.c`)

AP→STA 方向那一帧是直调 `esp_wifi_80211_tx()` 的, 失败既不计数也不上报。现在计入
`err`, 与正向帧一起出现在 DONE 行。

**OUI 表只有 40 条且有 5 条占位 Unknown** (`main/wifi_db.c`)

原来是手写表 + 线性查找, `0x28,0x15,0xA4` 这类条目直接写 "Unknown"。改为
`tools/gen_oui.py` 从 IEEE 注册表生成: App 侧 12166 条 (60 家精选, 不限条数),
固件侧 1963 条 (受 `vendor[16]` 与 flash 约束), 二分查找。

## 二、算法：做了什么，数据在哪

### 2.1 信道调度：SACS（已进固件，`--policy sacs`）

原来三套策略各有一个说不清的地方：`wrl` 按帧率给时间，热信道往往是"一台在刷
视频"，那里没有新目标；`psd` 按发现数排，但一轮 78 条信道要 21 秒；`adt` 短探针
加就地续期，速度上来了，却对空信道做指数退避，运行中上线的 AP 基本等不到回探。

SACS 换掉的是"还剩多少台"这个量怎么估：

- **剩余量**：每台 AP 独立发 beacon，累计暴露 E 后仍未发现的概率 s(E)，已发现
  k 台时 r = k·s/(1−s)。这是矩估计，没有可调参数。
- **生存函数用两成分混合**：0.75·e^(−E/bi) + 0.25·e^(−E/2bi)。现场有相当一部分
  AP 的 beacon 间隔是 2 倍周期，单成分模型会把它们的剩余量估成 0，最后一台永远
  等不到回探。这条直接对着尾延迟。
- **空信道用贝叶斯后验**：先验有货 q0=0.35，探过 E 仍没看到的后验是
  q0·s/(q0·s+1−q0)，所以探过没货的信道不会被永久判死。
- **回探间隔线性增长**：`2 + 连续空窗次数`，不做指数退避。指数退避在静态场景
  省时间，代价是中途上线的 AP 要等 4/8/16 轮。
- **驻留用饱和公式**：k≥2 时给 `bi·ln((k+2)/eps) − 已暴露`，差额补齐，上限 4×base；
  k<2 只给探针（base/3，base=300 时 100ms）。
- **解析结论**：把"单位时间期望新发现数"对驻留求极值，一阶条件
  e^(−x)(x+s/bi+1)=1 的解只跟切换开销有关，与台数无关。算出来 x≈0.56，
  即 57ms，低于探测下限，说明**驻留长度在探针之上没有信息量，决定性能的是
  选哪条信道**。这条把"驻留该给多少"从调参问题变成了结论。

仿真结果（300 局/场景，视界 45 秒，单位：中位找齐时间 / p90 / 未找齐比例）：

| 场景 | psd | adt | adt3 | sacs |
|---|---|---|---|---|
| default | 8.8 / 19.8 / 1% | 7.7 / 18.3 / 2% | 9.4 / 45.0 / 17% | **4.3 / 14.1 / 0%** |
| cold(+20 冷AP) | 32.2 / 45.0 / 31% | 45.0 / 45.0 / 53% | 45.0 / 45.0 / 81% | **24.0 / 43.2 / 8%** |
| late5g | **16.9 / 41.0 / 5%** | 16.8 / 45.0 / 13% | 15.9 / 45.0 / 43% | 20.6 / 31.1 / 3% |
| arrive(6 台中途上线) | 45.0 / 45.0 / 76% | 45.0 / 45.0 / 79% | 45.0 / 45.0 / 100% | **43.2 / 45.0 / 35%** |
| busy(单信道刷流量) | 8.7 / 18.0 / 1% | 7.9 / 18.4 / 3% | 12.9 / 45.0 / 16% | **4.3 / 14.0 / 0%** |

五个场景里四个全面领先，late5g 的中位慢 4 秒但 p90 好 10 秒、漏检从 5% 降到 3%。
参数用坐标下降在四个场景上选（权重按"漏一台等于多等 40 秒"折），不是手调的。

### 2.2 CSI 动作检测：主机测试挖出三个缺陷（已修）

把检测器编到主机上跑合成序列，三个问题在真机上根本看不出来：

1. **静止场景误报 96/120**。非对称增益（上行 0.002、下行 0.02）在平稳噪声上会让
   基线单向爬到低分位，之后噪声的上半部分全变成正偏差，CUSUM 一路累积。
2. **持续动作第 18 个样本就自我失明**。mad 以 5%/样本跟随 |偏差|，把动作幅度当成
   噪声学走，z 分数从 30 掉到 1.5，检测器主动退出。
3. **动作结束后卡住 30 多个样本**。判定为动作期间 CUSUM 还在累加，涨到 17，
   而退出条件要求"累积和已泄掉"。

改法：增益快慢只看"当前是否判定为动作"（动作期禁学当前电平），动作期冻结 mad，
动作期把 CUSUM 清零。现在：静止 0 误报、持续动作 200/200、动作结束 5 个样本内退出。

第 1 条的备选方案是"用偏差的慢均值判断是否持续偏移"，试过并且放弃了：基线一旦
追上去，慢均值自己就归零了，等于没判。

### 2.3 定位：补不确定度（已进固件）

原实现给 med/mad，趋势是"前后 25% 的中位数差"，但把 ±1dB 的抖动也当移动。

- 加了 `se`（中位数标准误 1.253·mad/√n）与 `ci`（趋势的 95% 半宽
  1.96·1.253·mad·√(2/k)·10/span）。
- 判据从"|slope|≥1 就算移动"改成"|slope| > ci"，`trend` 只有显著时才给 up/down。
- META 行新增 `se,slope,ci` 三个字段。

试过 Theil-Sen 斜率：20% 多径离群下中位绝对误差 0.18 vs 现有 0.22，只差 4%，
不值得 O(n²) 与额外代码。这个对比留在文档里，免得下次又想当然换。

### 2.4 握手槽位：按完整度淘汰（已进固件）

槽满时原来一律丢弃新目标。现场先扫到几个弱信号目标就能把 8 个槽占死，真正在
握手的那台一个位置都没有。改成挤掉"未完整且 RSSI 最弱"的那条，已完整的记录
不挤；全完整时仍然丢弃。

### 2.5 802.15.4 用完把 Wi-Fi 收包带走（P0，已修）

现象：`zbsniff 11` 起一次再 `stop`，之后 `sniff 6` 永远 `total=0`，`dump aps`
只剩几条 -90dBm 的残影。重启板子才恢复。扫全只验"每条命令后板子还活着"，
看不到这种串扰。

定位：把三种候选救法做成一条 `radio rearm phy|restart|promisc` 子命令，一次
构建逐个试。三种全部无效，说明不是时钟、不是驱动状态、也不是过滤没挂上。

根因：`esp_ieee802154_disable()` 内部是 `btbb_disable + rf_disable + mac_deinit`，
`mac_deinit` 会 `esp_intr_free` 掉与 Wi-Fi 共用的那条中断。Wi-Fi 以为自己还持有
这条中断，重启驱动时不会再 alloc，收包中断就彻底没了。

改法：关闭时只 `esp_ieee802154_sleep()`（只关射频，MAC 与中断留着），下次
`receive()` 自动唤醒；再加 `s_mac_up` 标志，让 `esp_ieee802154_enable()` 一辈子
只调一次（它本身也不幂等，二次调用报 `No free interrupt inputs`）。

验证：zbsniff 一次、两次、以及 zbtx 之后，`sniff 6` 分别收到 116 / 108 / 137 帧。

这类"功能 A 用完把资源还干净"的问题，要按"下一个功能还能不能用"来验。

### 2.6 真机对照（已跑）

`chan_ab.py` 交替跑两组，每次试验前清表，差异给 bootstrap 95% 区间。

- **12 秒窗口，psd vs sacs，各 10 次**：2/5/10 秒三个采样点差异分别是
  +0.0、-0.4、+0.0 台，区间都跨 0。这个环境 10 秒就饱和到 20/23，分不出来。
- 末轮驻留分配能看出机制差异：psd 给信道 1 分 600ms 找到 8 台；
  sacs 给 300ms 找到 9 台，同样的时间铺得更开。

结论写成这样：仿真里 SACS 的优势来自"少漏"（cold 场景漏检 8% vs psd 31%），
而漏检要在长窗口才看得见；12 秒短窗口两边都还没到分岔点。所以这个改动对
"15 秒扫一遍就走"的用法没有收益，对"长时间挂着，等有人上线"的用法才有。

### 2.7 还没做的

- CSI 的真实数据验证：未关联 AP 时收不到帧，这条限制没变，检测器的 ROC 只能在
  合成序列与 `csi selftest` 上看。
- 信道调度的真机对照：已经跑过 `chan_ab.py`，见第三节。

## 三、测试矩阵

分三类用例, 每条都带「预期」：留空 = 应正常执行, `reject` = 固件必须挡回来。

扫全 (`scripts/test_sweep.py`) 共 129 条 (本轮新增 SACS 与非法策略两条), 按族分布:

| 族 | 用例数 | 覆盖内容 |
|---|---|---|
| 扫描/嗅探 | 14 | scan / sniff 各信道与 auto / dump / status |
| 注入 | 24 | deauth、disassoc、auth、beacon、probe 五族的正常与非法参数 |
| 诱捕 | 11 | phish、karma、eviltwin、downgrade 的启停与前置条件 |
| 测量 | 8 | ftm、locate、csi 的采样与查询 |
| 无线 | 32 | raw 帧、bleadv 各类型、zbsniff/zbtx、ble 扫描与功率 |
| 数据 | 14 | cap 落盘、export csv/json、http 服务、config |
| 维护 | 12 | ota、health、selftest、version、reset |
| 其余 | 12 | help、log、job、stop、scenario |

每族都覆盖三类：正常参数、非法参数（应被 `reject`）、前置条件未满足（如没 scan
就 deauth）。判断依据全部来自固件回的 META 行, 不看"看起来正常"。

上面这支只验"没打死"。另加 `scripts/test_func.py` 验"真干成事"：嗅探有没有帧、
注入的 sent 对不对、门户起没起来、握手自检四条是否符合预期、落盘有没有抓到、
射频仲裁与事件总线有没有输出。

## 四、不建议做的

- 追 90% 找齐率。clairvoyant 上界说明现实策略首轮必须每条信道去一趟, 这条线在
  信道调度上不可达。
- 把 34k 条 OUI 全塞固件。flash 放得下, `vendor[16]` 放不下, 而且长厂名在 CLI 里
  更难读。
- 多射频并发。硬件就一个射频, 嗅探/注入/门户互斥是物理约束, 不是实现偷懒。
